# DongDa Structured Content

The public website uses structured JSON and shared validators/renderers to produce static pages and browser data. Content availability, a generated artifact and permission to publish are separate states. This README is copied into the public build; keep it free of private records, review evidence, credentials and operator-only details.

## Canonical Content

- `site-settings.json`: public brand/contact and deployment/SEO defaults. A target canonical domain is not proof that the domain is deployed.
- `products.json`: canonical product IDs/aliases, families, requested specifications, language copy, media roles and image references.
- `industries.json`: industry entities and explicit mappings to canonical products.
- `resources.json`: buyer requirement checklists, shared fields and canonical download text. These are not approved certificates or technical specifications.
- `insights.json`: buyer guides and their sections/FAQ; these are not independent company-news claims.
- `faqs.json`: FAQ mappings to existing canonical answers rather than duplicate answer text.
- `company-history.json`: the 20 preserved milestones and their existing translations.
- `company-profile.json`: company overview text and protected structure. Its initial legacy extraction is one-time; the seed script must not overwrite an existing file.
- `inquiry-schema.json`: shared procurement-input contract. The server independently validates submitted requests.
- `runtime-config.json`: public endpoint configuration only. Keep unaccepted endpoints unconfigured; endpoint presence is not proof of persistence or delivery.

Company and product facts, publication permissions, technical claims and existing review/noindex restrictions remain subject to their established review process. Editing text does not approve a fact, issue a new technical edition or change a protected source date.

## Compatibility And Generated Files

- `company.json` remains a legacy source for the general content index's base/journey records. Current company overview/history entities use `company-profile.json` and `company-history.json`; do not silently substitute one source for another.
- `news.json` is retained legacy source. `build:sites` excludes its source records and emits an empty public compatibility array. Public buyer guides use `insights.json`.
- `content-index.json` is generated by `build:content`; it includes compatibility company records. It is distinct from the public site-search index.
- `build:catalog` regenerates `assets/js/catalog-data.js`, including canonical catalog/industry/resource/insight/FAQ data and local icon nodes/licenses.
- `build:company` regenerates `assets/js/company-data.js` and the existing timeline hook in `index.html` from canonical company content.
- `build:sites` generates physical pages, route manifests, `content/site-search-index.json`, resource download manifests/files and fingerprinted assets inside the build output. Do not hand-edit generated files or treat a successful build as publication approval.

## Editing And Publication Boundaries

- Preserve stable IDs, aliases, product/image mappings, protected structures/dates/editions and review/noindex flags. Keep referenced image paths valid relative to the website root.
- Keep required Chinese/English/Russian text complete; preserve other existing translations and documented fallback behavior.
- Do not store secrets, API keys, mailbox passwords, database credentials, customer records or authorization tokens in public content or endpoint query strings.
- `private-review/` is private release-control material and is excluded from the public copy. Never move its records or evidence into public JSON, generated browser data, this README or public archives.
- Validate changes against the existing shared schemas. Regenerate affected derived files only in the selected, authorized build workspace: `build:content`, `build:catalog`, `build:company` and `build:sites` write files, and `build:sites` replaces that workspace's `dist` directory.
- Publish only through the established review and complete-artifact release process. Do not patch runtime configuration directly on public storage to bypass artifact validation or service acceptance.

This documentation update does not rebuild output, activate a release, configure a backend or establish new test results.
